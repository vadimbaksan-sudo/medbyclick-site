# Отчёт QA — регрессионный прогон после Phase 0

**Дата:** 2026-07-04
**Ответственный:** QA/GStack
**Цель тестирования:** Локальный dev-сервер (`http://localhost:3000`, `bun run dev`, Next.js 16.2.9 Turbopack)
**Примечание по цели:** По-прежнему нет задокументированного production/Vercel URL
нигде в репозитории (нет `.vercel/`, ничего в `docs/`) — тот же пробел, что был
отмечен в отчёте от 2026-07-02. Этот прогон снова выполнялся против локальной
сборки `main`.
**База для сравнения:** `docs/reports/qa/2026-07-02-first-e2e-qa-pass.md`
(до Phase 0, только мок-заглушки). Этот отчёт проверяет ту же поверхность
после того, как появились реальная аутентификация, реальная БД, реальный
букинг, реальный Stripe и реальный medai.
**Метод:** Два метода использовались вместе. (1) Headless-браузер skill из
gstack (`browse`, ниже обозначен как `$B`) для реального заполнения форм,
кликов, отправки, проверки консоли и сети, скриншотов. (2) `curl` для быстрого
прохода по статус-кодам всех маршрутов (главная, все 13 модулей, страницы
аутентификации, checkout, редиректы), чтобы подтвердить поведение маршрутизации
независимо от браузера. `bun test` также был запущен один раз как
дополнительный сигнал (см. «Юнит-тесты» ниже).
**Критическая оговорка по окружению (прочитать перед списком находок):** В этой
песочнице **нет `.env.local`** — нет реального проекта Supabase, нет
`DATABASE_URL`, нет ключей Stripe, нет `ANTHROPIC_API_KEY` (подтверждено: на
диске есть только `.env.example`). Код явно написан так, чтобы деградировать
без этих переменных (см. `lib/db/client.ts`, `lib/auth/dal.ts`), и именно это
поведение graceful degradation проверялось в этом прогоне. **Не удалось
проверить реальные, работающие на БД, happy-path сценарии** (действительно ли
реально зарегистрированный аккаунт попадает в `/dashboard` с реальным
содержимым; действительно ли реальный букинг сохраняется и появляется в
истории; действительно ли реальный Stripe PaymentIntent доходит до
завершения; действительно ли medai возвращает реальный структурированный
ответ). Для этого нужна стейджинг-среда с живым Supabase + тестовыми ключами
Stripe + ключом Anthropic, которых в этом окружении нет. Это самый большой
пробел покрытия в этом отчёте — см. «Не протестировано в этом прогоне».

## Что было проверено

`/`, `/register`, `/login`, `/dashboard`, `/doctor-dashboard`, `/book`,
`/checkout/stripe`, `/checkout/mbc`, `/checkout/crypto`, `/medai`, `/doctors`,
`/doctors/[id]` (3 реальных врача + 1 несуществующий slug), `/specialists`,
`/pricing`, и все 12 активных модулей (`medconnect`, `mededu`, `medtravel`,
`medcommunity`, `medevents`, `medsupport`, `medglobaldb`, `medtrials`,
`medpharmaccess`, `medtoken`, плюс `medai`/`medpayments` покрыты выше), а также
3 осиротевших легаси-маршрута (`education`, `ai-diagnostics`,
`medical-travel`). Интерактивное тестирование форм регистрации, логина,
`/book` (гейт для неавторизованных), `/checkout/stripe` (гейт для
неавторизованных) и medai (полное заполнение формы + отправка). Проверка
консоли и сети на каждом посещённом маршруте.

## Итог

**Платформа структурно держится: ноль ошибок JS-консоли и ноль сломанных
запросов/404 на всех проверенных маршрутах, и каждое «жёсткое требование» из
спецификации Phase 0, которое можно было проверить в этом окружении,
действительно выполняется** — гейты аутентификации на `/dashboard`,
`/doctor-dashboard`, `/book` и `/checkout/stripe` корректно отклоняют
неавторизованный доступ; фикс редиректов осиротевших страниц от 2026-07-02
по-прежнему держится; обе функции, зависящие от переменных окружения (Stripe,
medai), деградируют мягко с понятными сообщениями пользователю вместо падения.
**Три находки из отчёта 2026-07-02 теперь подтверждённо исправлены** (см.
«Исправлено с прошлого прогона»). Реальный пробел — это покрытие, а не
здоровье платформы: **это окружение не может провести ни один реальный
авторизованный сценарий от начала до конца**, потому что здесь не настроен
Supabase/БД, поэтому вопрос «действительно ли букинг сохраняется и появляется
в дашборде» остаётся непроверенным этим прогоном — так же, как он был
структурно непроверяем и раньше (до Phase 0), но по другим причинам.

## Главное, на что обратить внимание

1. **Эта песочница не может подтвердить реальный happy path, завязанный на
   БД** — регистрация, логин, сохранение букинга и дашборды врачей были
   проверяемы только на «мягко ли падает», а не на «работает ли корректно»,
   потому что здесь не настроен проект Supabase. CTO/Product стоит подключить
   стейджинг-проект Supabase + тестовые ключи Stripe до следующего прогона
   QA, иначе регрессии такого рода (например, тихий сбой записи букинга в БД)
   так и будут оставаться незамеченными до реальных пользователей.
2. **Саморегистрация врачей заспецирована, но не реализована** — несмотря на
   существование `docs/reports/product/2026-07-04-doctor-dashboard-spec.md`,
   код (`app/doctor-dashboard/page.tsx`, строка ~18) явно комментирует, что
   саморегистрация/редактирование профиля вне рамок этого прогона, а
   `lib/auth/actions.ts` строка 62 жёстко прописывает `role: "patient"` для
   каждой новой регистрации. Сейчас нет способа — ни в каком окружении —
   создать аккаунт врача через UI. Отмечаю это, чтобы никто не решил, что
   коммит со спецификацией означает, что функция уже работает.
3. **Хорошая новость, не баг:** три проблемы из базового отчёта 2026-07-02
   теперь исправлены — см. ниже.

## Исправлено с прошлого прогона

- **Предупреждение о демо-режиме в крипто-checkout (было High-находкой №1).**
  `/checkout/crypto` теперь показывает чёткий баннер `⚠️ DEMO / TEST MODE — эта
  страница не подключена к реальному кошельку или блокчейну. Не отправляйте
  реальные USDT...` и помечает адрес депозита как «Demo address — do not send
  funds». Проверено вживую через `$B`: `/pricing` → выбор плана → USDT
  (ERC-20) → Pay Now → подтверждено отображение баннера и метки.
- **Дублирование списка врачей (было High-находкой №2).** `/doctors`,
  `/specialists` и `/medconnect` теперь все импортируют из единого источника
  (`modules/medconnect/data.ts`) — подтверждено через `grep`, что ни один файл
  страницы больше не хардкодит имена врачей (только моковые данные
  `mededu`/`medevents` упоминают имена врачей, но это не список специалистов,
  а несвязанный контент).
- **Осиротевшие страницы (было Medium-находкой №3).** `/education`,
  `/ai-diagnostics`, `/medical-travel` теперь делают 308-редирект на
  `/mededu`, `/medai`, `/medtravel` соответственно (подтверждено через
  `curl -D -` и через браузер — страница не рендерится до срабатывания
  редиректа, устаревший контент не отдаётся).
- **Формы логина/регистрации не давали обратной связи (была Low-находкой
  №4).** Обе формы теперь показывают понятное сообщение при отправке — в этом
  окружении это «Registration is not available yet — the Supabase project
  and database have not been configured in this environment. Please contact
  support», что является корректным сообщением для ненастроенной песочницы, а
  не живым багом. Сам механизм (форма → server action → сообщение
  пользователю) работает.

## Находки

### 1. [Информационно / пробел окружения] Нет живых credentials Supabase, Stripe или Anthropic в этой песочнице — реальные авторизованные сценарии непроверяемы в этом прогоне
- **Воспроизведение:** `ls .env.local` → не найден; есть только
  `.env.example`. `isDatabaseConfigured()` из `lib/db/client.ts` возвращает
  false; `verifySession()` из `lib/auth/dal.ts` сразу возвращает `null`, если
  Supabase не настроен.
- **Почему это важно:** Каждый вопрос «действительно ли X работает от начала
  до конца» из задания (регистрация → дашборд с реальным содержимым, логин с
  тем же аккаунтом, букинг → история в дашборде, дашборд врача с реальным
  аккаунтом врача, завершение Stripe PaymentIntent, реальный структурированный
  ответ medai) сводится в этом окружении к «падает ли мягко вместо краша» —
  что подтверждено (см. находки 2–4) — но это не то же самое, что «работает».
  Реальная регрессия, скажем, в SQL-запросе на вставку букинга или в
  обработчике вебхука платежей была бы невидима для любого QA-прогона в таком
  окружении.
- **Доказательства:** отсутствие `.env.local` на диске; сообщения о мягкой
  деградации, показанные в находках 2–4 ниже.
- **Рекомендация:** Не баг в коде — пробел QA-инфраструктуры. CTO/Product
  стоит развернуть стейджинг-проект Supabase + тестовые ключи Stripe (+
  опционально недорогой ключ Anthropic), доступный следующему QA-прогону,
  чтобы можно было проверить реальные пути записи в БД, а не только их
  fallback-пути.

### 2. [Подтверждённо работает] Жёсткий гейт аутентификации на `/dashboard` и `/doctor-dashboard` держится
- **Воспроизведение:** `curl -D - http://localhost:3000/dashboard` → `307` с
  `location: /login`. То же для `/doctor-dashboard`. Подтверждено повторно
  реальным браузером на обоих URL — итоговый URL после навигации в обоих
  случаях `http://localhost:3000/login`.
- **Почему это важно:** Это было явное жёсткое требование из задания —
  проверено, что оно действительно выполняется, а не только по код-ревью.
- **Доказательства:** заголовки curl; `$B url` после `$B goto` на обоих
  маршрутах.

### 3. [Подтверждённо работает] Гейт аутентификации теперь также покрывает `/book` и `/checkout/stripe`, корректно
- **Воспроизведение:** Неавторизованный `/book` показывает «Log in to book a
  consultation» с кнопками Log in / Create an account вместо формы букинга
  (`app/book/page.tsx`). Неавторизованный `/checkout/stripe` пытается сделать
  `POST /api/payments/stripe/create-intent`, получает `401`, и UI показывает
  «Please log in to make a payment. Log in and try again» — без краша, без
  показа стека вызовов, без обращения к ключу Stripe до того, как сработает
  проверка авторизации.
- **Почему это важно:** Это новое с прошлого прогона от 2026-07-02 (тогда
  Stripe Elements загружался вообще без проверки авторизации) — букинг и
  платежи теперь корректно привязаны к проверенной личности, согласно
  спецификации §3.2, а не к полю имя/email, которое мог бы подделать клиент.
- **Доказательства:** `$B network`, показывающий `401` на `create-intent`;
  `$B text`, показывающий приглашение войти.

### 4. [Подтверждённо работает] medai мягко падает без API-ключа
- **Воспроизведение:** `/medai` → заполнить описание симптомов + длительность
  + тяжесть + возраст → «Send to Coordinator» → UI показывает «Something went
  wrong — We couldn't process your intake right now. Please try again
  shortly, or describe your symptoms to a coordinator directly.» с кнопкой
  «Try again». Исходный запрос: `POST /api/medai/intake` → `502`. Лог
  dev-сервера подтверждает реальную причину: `[medai/intake] Anthropic
  request failed Error: Could not resolve authentication method... Or for one
  of the "X-Api-Key" or "Authorization" headers to be explicitly omitted` —
  то есть именно ожидаемый режим отказа для «нет ANTHROPIC_API_KEY в этой
  песочнице», а не дефект кода.
- **Почему это важно:** Подтверждает, что intake-флоу деградирует безопасно —
  пациенту не показывается стек вызовов, нет ошибки, ломающей консоль, а
  дисклеймер о неотложной помощи («If this is an emergency...») присутствует
  над формой независимо от доступности бэкенда.
- **Доказательства:** дамп текста ошибки из браузера; `502` в `$B network`;
  строка лога ошибки сервера выше.

### 5. [Информационно] Саморегистрация врачей ещё не существует — невозможно создать тестовый аккаунт врача ни в каком окружении сейчас
- **Воспроизведение:** На `/register` нет выбора роли (`grep -n "role"
  app/register/RegisterForm.tsx` → совпадений нет); `lib/auth/actions.ts:62`
  жёстко прописывает `role: "patient"` при каждой регистрации.
  `app/doctor-dashboard/page.tsx` в собственном комментарии заявляет, что
  саморегистрация/редактирование профиля «explicitly NOT» в рамках текущего
  прогона.
- **Почему это важно:** В задании просили протестировать `/doctor-dashboard`
  «как тестовый аккаунт с ролью врача, если можно его создать» — подтверждено,
  что сейчас нет способа его создать через UI, даже с полностью настроенным
  проектом Supabase. Аккаунт врача сейчас может существовать только через
  прямой сид БД (`bun run db:seed`), не через самообслуживание. Это известный,
  заспецированный пробел (не регрессия) — отмечаю, чтобы следующий прогон или
  Product не решили, что недавний коммит со спецификацией означает, что
  функция уже в проде.
- **Доказательства:** результаты grep выше; комментарий в коде
  `app/doctor-dashboard/page.tsx`.

## Что сработало хорошо

- Ноль ошибок JS-консоли на всех повторно протестированных маршрутах в этом
  прогоне (26+ маршрутов, проверено с очищенным буфером консоли перед каждой
  навигацией): главная, все страницы модулей, checkout/*, страницы
  докторов/специалистов/детальные, целевые страницы редиректов-сирот.
- Ноль сломанных сетевых запросов (кроме намеренно протестированных путей
  отказа 401/502 в находках 3–4, которые корректны по замыслу, а не баги).
- `/doctors/nonexistent-slug` по-прежнему корректно отдаёт 404.
- Все 13 страниц модулей, `/pricing`, `/checkout/mbc`, `/checkout/crypto`
  по-прежнему возвращают чистые 200 без ошибок консоли.
- Полный проход по ссылкам главной страницы (`$B links`) не нашёл битых
  ссылок — каждая ссылка в шапке/подвале/сетке модулей ведёт на существующий
  маршрут.
- `bun test`: 46/50 проходят. Все 4 падения — в `contracts/test/*` (набор
  Hardhat/BNB-chain для смарт-контрактов — область Phase 4/токена по
  roadmap, не связана с этим прогоном по Phase 0 веб-части) и падают с
  `HardhatError: You are not inside a Hardhat project` — отсутствующая
  конфигурация Hardhat в этой песочнице, а не регрессия кода. Реальный набор,
  относящийся к Phase 0, `modules/medai/intake.test.ts`, проходит полностью
  (его логируемые в консоль «ошибки» — намеренные проверки замоканных путей
  отказа, а не настоящие падения).

## База для регрессии

Этот отчёт заменяет `2026-07-02-first-e2e-qa-pass.md` в качестве текущей базы
для сравнения. Три находки из того отчёта теперь закрыты (см. «Исправлено с
прошлого прогона»). High-находка про placeholder-кошелёк в крипто-checkout,
High-находка про дублирование списка врачей и Medium-находка про
осиротевшие страницы — все решены. Новых технических регрессий в том, что
можно было протестировать в этом окружении, не найдено.

## Не протестировано в этом прогоне

- **Реальный авторизованный happy path целиком** — реальная регистрация →
  реальная сессия → `/dashboard`, показывающий реальные (пусть даже пустые)
  разделы букингов/платежей/медицинской истории; реальный логин с тем же
  аккаунтом; реальный букинг, действительно сохраняющийся в Postgres и
  появляющийся в истории дашборда; реальный аккаунт врача, видящий реальные
  назначенные букинги; реальный Stripe PaymentIntent, доходящий до
  подтверждённого/успешного статуса; реальный ответ LLM от medai. Всё
  заблокировано отсутствующими credentials `.env.local` в этой песочнице (см.
  находку 1) — это пробел окружения, а не то, что можно было обойти в рамках
  этого прогона.
- Реальный production-деплой на Vercel (URL по-прежнему не задокументирован —
  тот же пробел, что и 2026-07-02).
- Кросс-браузерность (только headless Chromium).
- Нагрузочное/производительное тестирование.
- Мобильная/адаптивная вёрстка (повторно не проверялась в этом прогоне; была
  чистой в прогоне 2026-07-02, и в просмотренных диффах не замечено изменений,
  влияющих на вёрстку).
