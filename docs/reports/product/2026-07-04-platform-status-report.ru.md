# Отчёт о статусе платформы — 2026-07-04

Автор: **CTO/Product** (`docs/agents/CTO_PRODUCT.md`) · Тип: отчёт о статусе, не спецификация

## Зачем этот документ

Вадим прямо спросил, почему он не получает консолидированный отчёт о статусе
продукта — он получает отдельные технические отчёты от Web3, Legal, Medical
Advisory и Developer, но никто прямо не сказал, где реально находится
платформа. Это — такой отчёт. Он основан на чтении текущего кода и на
реальном запуске приложения (`bun run dev` + `curl` по всем маршрутам, плюс
набор unit-тестов) — а не на желаемых описаниях из роадмапа. Таблицы Phase
0/1 в `docs/ROADMAP.md` обновлены на месте под это; этот документ —
развёрнутая версия того обновления плюс находки по клик-тесту и список
приоритетов, которых в роадмапе нет.

## Главное

**Основной пользовательский цикл (регистрация → вход → бронирование → оплата
→ medai → личный кабинет) теперь реально работающий код** — большой скачок
по сравнению с базовой линией роадмапа от 2026-07-02, где не было вообще
ничего, кроме мок-данных. Но **сегодня ничего из этого нельзя реально
пройти по клику**, ни в одном окружении, потому что никто не подключил
реальный проект Supabase, реальный аккаунт Stripe или ключ Anthropic API.
Каждый поток корректно завершается понятным сообщением «не настроено —
обратитесь в поддержку», а не падает и не имитирует успех — это правильное
защитное поведение, но честный ответ на вопрос «работает ли это от начала
до конца» такой: **код есть, подключение к внешнему миру — нет.** Это
организационный/закупочный пробел, а не инженерный — см. пункт 1 в списке
приоритетов.

Остальные 8 из 13 модулей остаются точно такими же, какими были 2026-07-02:
это фронтенд-заглушки на мок-данных без какой-либо базы данных за ними.

## Статус по модулям

| Модуль | Статус | Детали |
|---|---|---|
| `core` (аутентификация/БД/личность) | **Реальный код, пока недоступен** | Supabase Auth + схема Drizzle/Postgres; регистрация/вход/выход — реальные Server Actions; проверки сессии (`getCurrentUser`/`requireUser`/`requireRole`) реально защищают каждую защищённую страницу и Server Action, а не только опциональный редирект в Proxy. Живого проекта Supabase/`DATABASE_URL` пока нигде нет — каждый вызов корректно откатывается к сообщению об ошибке. |
| `core` — история болезни / анализы | **UI-заготовка, намеренно на синтетике** | В личном кабинете видна чётко помеченная панель «синтетические примерные данные — ожидает проверки Legal & Compliance». Реального пути чтения/записи ещё нет — это правильно, пока не завершится юридическая проверка (она уже прошла и предложила модель доступа). |
| `medconnect` (бронирование) | **Бронирование реально; страницы просмотра врачей всё ещё моки** | Само бронирование (`/book` → Server Action → реальная запись в `bookings` → видна и в кабинете пациента, и в кабинете врача) полностью реально и защищено авторизацией. Но три маркетинговые страницы со списком врачей (`/medconnect`, `/doctors`, `/specialists`) всё ещё читают статический массив, а не базу данных — см. пункт 3 в списке приоритетов. Саморегистрация врачей и редактирование профиля специфицированы, но не реализованы; сегодня врачей можно завести только вручную, и врач может только просматривать свои бронирования, но не действовать по ним. |
| `medglobaldb` | **Мок** | Та же проблема со статическим массивом; готовая функция запроса к БД (`listGlobalDbDoctors`) существует, но просто не вызывается. |
| `medai` | **Реальный код, пока недоступен** | Реальный вызов Claude (Haiku 4.5) для структурированного сбора симптомов с детекцией «красных флагов», после проверок Legal и Medical Advisory; ограничен синтетическими/тестовыми данными. `ANTHROPIC_API_KEY` не настроен, поэтому возвращается понятная ошибка 503 вместо реальной работы. |
| `medpayments` (Stripe/фиат) | **Реальный код, пока недоступен** | Серверное создание PaymentIntent, подтверждение через webhook, сохранённые чеки, история платежей в кабинете — всё реально. Реального аккаунта/ключей Stripe нет; публичный ключ откатывается на общий демо-ключ Stripe, который корректно проваливается на этапе подтверждения (не имитирует «успех»). |
| `medpayments` (MBC / крипто-оплата) | **Полностью мок, и это правильно** | Баланс в `localStorage` + кнопка «подтвердить» вручную, без подключения кошелька или проверки в блокчейне — верно отложено до Фазы 4 вместе с токен-контрактом. |
| `mededu`, `medcommunity`, `medevents`, `medpharmaccess`, `medsupport`, `medtoken`, `medtravel`, `medtrials` | **Полностью моки, без изменений** | Каждый — это всё ещё `types.ts` + статичный `data.ts` + один презентационный компонент-карточка. Ни базы данных, ни реального workflow. Полностью соответствует исходной базовой линии роадмапа от 2026-07-02 — регресса нет, но и прогресса с той даты тоже нет. |

## Что я проверил, реально запустив приложение

Запустил `bun run dev` и проверил через `curl` каждый маршрут верхнего
уровня и каждого модуля (26 маршрутов): все возвращают 200 (с учётом
редиректов), ничего не падает с 500-й ошибкой. В частности проверено:

- **Защита авторизацией работает корректно**: `/dashboard` и
  `/doctor-dashboard` корректно делают 307-редирект на `/login` для
  неавторизованных пользователей (это серверная проверка, а не только
  опциональная проверка в Proxy). `/book` показывает правильный экран
  «войдите, чтобы забронировать» вместо самой формы.
- **Редиректы со старых маршрутов всё ещё работают**: `/education`,
  `/ai-diagnostics` и `/medical-travel` (страницы, заменённые на `/mededu`,
  `/medai`, `/medtravel` в QA-проходе от 2026-07-02) по-прежнему корректно
  делают 308-редирект через `next.config.ts`. Недавняя работа над
  medai/doctor-dashboard не создала новых дублей — я проверил это отдельно
  по промежуточной корректировке задачи и подтвердил, что фикс на месте.
- **Unit-тесты**: 46 из 46 продуктовых тестов проходят (валидация
  авторизации/бронирования, унификация seed-данных врачей, логика
  medai-intake и «красных флагов»). Запуск `bun test` в корне репозитория
  также показывает 4 ошибки, но они происходят из-за того, что в тот же
  тестовый прогон попадает Hardhat-подпроект из `contracts/` — это не
  регресс продукта.

## Найдено при клик-тесте: три почти одинаковые страницы врачей

`/specialists`, `/doctors` и `/medconnect` — три отдельных маршрута с почти
идентичным текстом и вёрсткой, и все три показывают один и тот же
статический мок-список врачей. Это не новая проблема (существовала и
раньше), но её стоит исправить вместе с пунктом 3 ниже — как только одна из
страниц будет подключена к реальной таблице `doctor_profiles`, две другие
должны на неё редиректить, а не оставаться параллельными расходящимися
копиями.

## Список приоритетов

1. **Подключить реальные аккаунты вендоров** — проект Supabase +
   `DATABASE_URL`, реальный аккаунт Stripe (тестового режима достаточно для
   старта) и ключ Anthropic API — и передать их через `.env.local` по
   образцу `.env.example`. Это организационная/закупочная задача для
   Вадима, а не для разработки, и это единственный блокер, мешающий
   кому-либо пройти по клику регистрацию → бронирование → оплату → medai
   где бы то ни было. Ничего из списка ниже не имеет смысла без этого шага.
2. **Прогнать миграции Drizzle + seed-скрипт на реальной БД** после
   подключения, затем сделать один реальный ручной прогон: зарегистрировать
   пациента, забронировать консультацию, оплатить тестовой картой Stripe,
   пройти medai-intake, убедиться, что всё корректно отображается и в
   кабинете пациента, и в кабинете врача.
3. **Переключить `/medconnect`, `/medglobaldb`, `/doctors`, `/specialists`
   на реальный слой запросов `doctor_profiles`** (`lib/db/queries/doctors.ts`
   — уже реализован, просто не используется) вместо статических мок-массивов.
   Сейчас реальное бронирование может ссылаться на врача, которого страницы
   просмотра вообще не показывают, и наоборот.
4. **Реализовать спецификацию-продолжение по кабинету врача**
   (саморегистрация, редактирование профиля, действия по статусу
   бронирования), чтобы аккаунты врачей перестали требовать ручного
   создания, а врачи могли не только просматривать, но и действовать по
   своим бронированиям.
5. **Объединить три дублирующие страницы со списком врачей** в одну, после
   выполнения пункта 3.
6. Всё остальное (mededu, medcommunity, medevents, medpharmaccess,
   medsupport, medtoken, medtravel, medtrials) — это реальная работа, но
   правильно стоит ниже по приоритету: ничто из этого не блокирует основной
   цикл «работает ли платформа», о котором сейчас спрашивает Вадим.
