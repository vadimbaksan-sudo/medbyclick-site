**Внешние ключи в `lib/db/schema.ts`** (подтверждено прямым чтением файла):
- `users` (1) —1:1— `patientProfiles` / `doctorProfiles` (оба ключуются по `users.id`, но
  `doctorProfiles.userId` **nullable** — у сид-врачей ещё нет логина).
- `bookings.patientId` → `users.id` (обязательно); `bookings.doctorId` → `doctorProfiles.id`
  (nullable, и намеренно **не** `userId` — это позволяет бронированию указывать на ещё не
  онбордингованного сид-врача).
- `payments.userId` → `users.id`; `payments.bookingId` → `bookings.id` (nullable).
- `medicalHistoryEntries.patientId` → `users.id`; `.doctorId` → `doctorProfiles.id` (nullable).
- Поля направления поездки: `bookings.travelDirection` (enum: `patient_travels`/`doctor_travels`) +
  `bookings.travelCountry` — на `bookings`, nullable, только для medtravel;
  `doctorProfiles.availableForMissionTravel` — булево поле, явно помечено как **не редактируемое
  самим врачом** — только админ/Medical Community может его менять.

## 2. Саморегистрация/дашборд врача: спецификация есть, реализации нет

Проверено напрямую: `9334e4b` добавил `docs/reports/product/2026-07-04-doctor-dashboard-spec.md` —
это только документ-спецификация от CTO/Product (по правилу "Must-Not-Do" этой роли — специфицирует,
не реализует). Ни один коммит после него не трогает файлы, которые требует спецификация. Конкретно:

- `app/doctor-dashboard/page.tsx` **не изменён** с исходной сборки Фазы 0 — `requireRole("doctor")` +
  список бронирований только для чтения. Нет просмотра профиля, редактирования, действий со статусом.
- **Маршрут `/register/doctor` не существует.** `registerPatient()` в `lib/auth/actions.ts`
  по-прежнему жёстко задаёт `role: "patient"` с собственным комментарием: "саморегистрация врача
  явно вне рамок этого прохода".
- **`lib/doctor-profile/actions.ts` (рекомендованный спекой `updateOwnDoctorProfile`) не существует.**
- **Функции изменения статуса бронирования не существует вовсе** — в `lib/db/queries/bookings.ts`
  только `createBooking`, `listBookingsForPatient`, `listBookingsForDoctorProfile`,
  `findDoctorProfileBySlugOrId`. Нет `updateBookingStatus`/подтвердить/завершить/отклонить.

**Вывод: реализовано 0%.** Спецификация качественная и готова для передачи разработчику, но ничего
из описанного — саморегистрация, whitelist самостоятельного редактирования профиля, действия с
бронированиями — не попало в код. Нужна новая постановка задачи разработчику, а не "долепить хвост".

## 3. Состояние безопасности/аутентификации: DAL применяется последовательно, пробелов не найдено

`lib/auth/dal.ts` — единый DAL: `verifySession()` использует `getUser()` Supabase (не `getSession()`,
корректно избегая задокументированной ловушки доверия куки), `requireRole()` для серверных
компонентов, `getAuthorizedUser()` для Server Actions/Route Handlers. Проверены все защищённые
поверхности, добавленные сегодня:

- `app/dashboard/page.tsx`, `app/doctor-dashboard/page.tsx` — `requireRole(...)`.
- `lib/bookings/actions.ts` — `getAuthorizedUser(["patient"])`, корректно ограничено.
- `app/api/payments/stripe/create-intent/route.ts` — `getAuthorizedUser()`.
- `app/api/payments/stripe/webhook/route.ts` — корректно **не** использует DAL; вместо этого
  проверяет подпись Stripe, что правильно для серверного колбэка от вендора, а не пробел.

Пропусков DAL не найдено. Пока последовательно — но по сути ещё не с чем сравнивать регресс, так как
доработка дашборда врача (§2) ещё не написана; требование whitelist из спецификации (никогда не
пускать `vettingStatus`/`verified` и т.п. в парсируемые ключи Zod) — то, за чем нужно следить, когда
эта работа начнётся.

## 4. Известные открытые пробелы (сверено с сегодняшними отчётами)

1. **`medical_history_entries` остаётся только синтетическим.** Обзор Legal & Compliance
   (`docs/reports/legal/2026-07-04-medical-history-data-handling-review.md`) нашёл *больше* блокеров,
   чем ожидалось: нерешённый конфликт хранения/удаления, невыбранный регион хостинга (рекомендует ЕС,
   не США, до готовности израильской структуры), неподтверждённая политика шифрования/контроля
   доступа для хранилища. Ничего из этого не закрыто — не подключать реальные данные пациентов к
   этой таблице.
2. **Стандарт вёттинга врачей требует полей схемы/работы, которые Medical Community отметила, но
   никто не реализовал**: номер лицензии, статус проверки на дисциплинарные взыскания, контакты
   рекомендателей отсутствуют в `doctorProfiles`, и **нигде нет админ-интерфейса**, чтобы перевести
   `vettingStatus` из `pending` в `approved` — сегодня это возможно только прямым доступом к БД.
3. **Смена модели `medai` на Haiku 4.5 поведенчески не проверена.** Обзор Medical Advisory явно
   говорит: ни одного реального вызова модели не протестировано на правила "без диагноза/без
   лечения/без успокоения"; защита на уровне схемы всё ещё действует, но выбор модели не будет
   подтверждён, пока тест не проведён.
4. **Саморегистрация/дашборд врача (§2) требуют полной реализации**, а не доработки — ничего не
   попало в код.
5. **Нигде нет живых учётных данных вендоров** — проект Supabase, аккаунт Stripe и ключ Anthropic API
   всё ещё должны быть предоставлены Вадимом, прежде чем "реальный код" Фазы 0/1 станет действительно
   доступен целиком.

## 5. DESIGN.md против реального кода: найдено одно реальное расхождение

Исправление цветов аватаров на главной/`/specialists`/`/doctors`/странице врача (`93ba057`, попало в
код **до** принятия `DESIGN.md` в тот же день) добавило `lib/ui/avatarColor.ts` — палитру градиентов
из 8 цветов: янтарный, **бирюзовый**, розовый, индиго, изумрудный, небесный, фуксия, лайм —
применяется к аватарам врачей на всех медицинских trust-страницах.

Раздел "Color" в `DESIGN.md` прямо это нарушает по двум пунктам:
- "сдержанно — **один акцентный цвет на контекст**, цвет редок и осмысленен, никогда не повторяющееся
  украшение" — вращающаяся палитра из 8 цветов — это противоположность.
- "Строго ограничен поверхностями экосистемы/токена/образования... **Не использовать бирюзовый на
  медицинских trust-страницах**" — бирюзовый градиент из `avatarColor.ts` сейчас отображается на
  главной, `/specialists`, `/doctors` и странице врача — все они являются trust-страницами по
  собственному определению `DESIGN.md`.

Исправление фильтра специальностей (`8d8b492`) и нерабочей кнопки фильтра новых цветов не вводит —
используются существующие классы slate/amber, и это соответствует `DESIGN.md`. Страницы `medtoken`
уже корректно используют бирюзовый (единственное место, где он уместен).

**Рекомендация разработчику**: заменить палитру из 8 градиентов в `avatarColor.ts` на небольшой набор,
соответствующий `DESIGN.md` (например, 2-3 тональных варианта янтарного/сланцевого, или единая
последовательная обработка) — различимость по врачам можно сохранить без внебрендовой радуги цветов
на trust-страницах.
