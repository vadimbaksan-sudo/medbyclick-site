## 1. Авторизация и базовая модель пользователя

### 1.1 Что значит «реальная» авторизация здесь

Реальная авторизация = идентичность, проверяемая сервером (не `localStorage`), пароль (или эквивалент), который реально хешируется, токены сессии, которые невозможно подделать и можно отозвать, и система ролей (`patient` / `doctor` / `admin`), применяемая на сервере на каждом защищённом маршруте и Route Handler'е — а не просто спрятанная в UI. Поле `User.role` в `modules/core/types.ts` — вполне нормальная стартовая форма; оставить его, но сейчас оно ничего не делает.

### 1.2 Действительно нестандартная особенность Next.js (прочитать перед написанием любого кода авторизации)

`AGENTS.md` этого репозитория — не декорация: это Next.js **16.2.9**, и прямое чтение `node_modules/next/dist/docs/01-app/02-guides/authentication.md` (гайд, поставляемый именно с этой версией) выявило две конкретные вещи в духе breaking changes, которые Developer должен знать до старта:

1. **Middleware в этой версии называется Proxy, и это другой файл.** Собственный пример оптимистичной проверки авторизации из гайда написан против `proxy.ts` (не `middleware.ts`), с `export default async function proxy(req)`. Кто угодно, кто будет действовать по шаблону из туториалов до-16-й версии Next.js (где везде `middleware.ts`), молча напишет файл, который Next 16 никогда не вызовет. Нужно свериться с точным названием файловой конвенции и её расположением в `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/`, прежде чем строить защиту маршрутов таким способом.
2. **`forbidden()`/`unauthorized()` — экспериментальные и включаются флагом конфигурации.** `node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/authInterrupts.md` подтверждает, что эти две функции (чистые примитивы 401/403 из API reference) работают только если в `next.config.js` установлено `experimental: { authInterrupts: true }`, и связанные файловые конвенции (`app/api-reference/file-conventions/forbidden.md`, `unauthorized.md`) нужно прочитать, чтобы использовать их правильно. Нужно один раз заранее решить: включать этот флаг и использовать встроенные примитивы, или вручную формировать ответы 401/403 (как уже делает `app/api/medai/intake/route.ts` через обычный `NextResponse.json(..., { status: 401 })`) — не смешивать оба подхода в разных маршрутах.

Ни один из этих пунктов не блокирует выбор ниже, но какой бы подход к авторизации ни был выбран, Developer обязан заново вывести точную форму Route Handler / Proxy / cookie API из документации в `node_modules/next/dist/docs/` для установленной версии, а не из тренировочных данных о том, «как обычно работает авторизация в Next.js». Это самый вероятный источник молча сломанного флоу авторизации в этой сборке.

### 1.3 Варианты (решение по вендору/стоимости — решает Вадим)

### 1.4 Рекомендация

**Вариант C — Supabase (Auth + Postgres вместе).** Обоснование: этой сборке одновременно нужна и реальная система авторизации, и реальная база данных (по §2 решение по БД не опционально и не откладываемо — оно блокирует и запись на приём, и платежи, и медицинскую историю). Покупка обоих у одного вендора схлопывает два цикла вендорских решений в один, даёт row-level security Postgres как естественный слой контроля доступа для «пациент может читать только свою медицинскую историю / врач может читать бронирования только назначенных ему пациентов» (именно такая форма контроля доступа нужна этому продукту), и избавляет от необходимости писать безопасность сессий/паролей вручную для продукта, который будет хранить данные о здоровье. Стоимость вендорской зависимости реальна, но приемлема на этом этапе — альтернатива (кастомный Auth.js + отдельно хостящаяся БД) требует больше суммарной интеграционной работы, чтобы сделать её правильно с первого раза силами двух-человечной команды с AI-конвейером разработки, а цена ошибки в безопасности сессий на продукте с данными о здоровье асимметрично выше цены вендорской зависимости.

**Это решение Вадима на подтверждение, а не то, что я закрываю единолично** — отмечаю согласно ограничению этой роли: реальная регулярная стоимость вендора, выбрать до старта Developer'а.

### 1.5 Следствие для базовой схемы

Оставить `User.role: "patient" | "doctor" | "admin"` из `modules/core/types.ts` — форма уже правильная. Какой бы вариант ни был выбран, поле `role` должно проверяться на сервере (проверка через Route Handler / DAL по паттерну Data Access Layer из гайда по авторизации Next 16 — см. раздел «Creating a Data Access Layer (DAL)» в `node_modules/next/dist/docs/01-app/02-guides/authentication.md`), никогда не доверяясь клиентскому состоянию или скрытому через UI-условия — гайд явно предостерегает от «SPA-паттерна» с `return null` для неавторизованных пользователей, потому что множественные точки входа Next (Server Actions, Route Handlers, вложенные сегменты) могут быть вызваны напрямую независимо от того, что рендерит layout.

## 2. Выбор базы данных и схема

### 2.1 Варианты (решение по вендору/стоимости — решает Вадим, связано с §1.4, если выбран Supabase)

| Вариант | Плюсы | Минусы | Стоимость |
|---|---|---|---|
| **A. Supabase Postgres + Drizzle или JS-клиент Supabase** | В комплекте с вариантом C авторизации выше; управляемый Postgres; встроенная row-level security; щедрый бесплатный тариф для масштаба MVP | Вендорская зависимость (общая с решением по авторизации) | Бесплатный тариф, затем оплата по использованию |
| **B. Neon (serverless Postgres) + Drizzle ORM** | Лучший в своём классе serverless Postgres (ветвление, масштабирование до нуля — дёшево при низком раннем трафике); Drizzle лёгкий, типобезопасный и компактнее Prisma; развязан с вендором авторизации, поэтому подходит и к варианту A (Auth.js), и к варианту B выше независимо | Ещё одни отношения с вендором, если Supabase (авторизация) выбран отдельно; нет встроенной авторизации, поэтому естественно сочетается с вариантом A (Auth.js), а не C | Бесплатный тариф щедрый; оплата по использованию сверх него |
| **C. Vercel Postgres (на основе Neon) + Prisma** | Самая простая эксплуатационная история, если уже деплоите на Vercel; у Prisma самая большая экосистема/документация, проще всего сделать правильно с первого раза для AI-управляемого цикла разработки, так как это самая задокументированная ORM в тренировочных данных | Рабочий процесс миграций схемы у Prisma тяжелее, чем у Drizzle; исторически чуть выше латентность холодного старта по сравнению с Drizzle + чистый SQL | Тарифы Vercel Postgres — свериться с актуальными цифрами перед принятием решения |

### 2.2 Рекомендация

**Если для авторизации в §1.4 выбран вариант C (Supabase): использовать собственный экземпляр Postgres от Supabase, с запросами через Drizzle ORM** (у Drizzle есть задокументированный путь интеграции с Supabase, и он оставляет код запросов типобезопасным и близким к чистому SQL — его проще аудировать для продукта с данными о здоровье, чем абстракции, генерируемые более тяжёлой ORM).

Если Вадим переопределит §1.4 и выберет для авторизации вариант A или B вместо этого, то **Neon + Drizzle** — запасная рекомендация по БД; ORM в любом случае та же, поэтому код запросов Developer'а не придётся менять, если решение по вендору сместится позже.

  — заменяет фейковый setTimeout-успех из app/book/BookForm.tsx на сохранённую запись

payments
  id, user_id (FK), booking_id (FK, nullable — не все платежи привязаны к бронированию,

  succeeded | failed | refunded, provider: stripe (другие позже),

  — это и есть таблица сохранённых чеков, которую требует строка Фазы 0 в роадмапе

  id, patient_id (FK users), entry_type: visit_note | lab_result | prescription
  | diagnosis, doctor_id (FK, nullable — часть записей загружает сам пациент, а не

  Developer может разбить на типизированные таблицы позже, когда станут известны
  реальные паттерны использования. Только структура — см. §5, почему хранение

Это намеренно концептуально — Developer проектирует реальный DDL, индексы, ограничения внешних ключей и файлы миграций. ## 3. Спецификация флоу записи на приём (`medconnect` / `medglobaldb`)

### 3.1 Решить пересечение профилей врачей сейчас (открытый вопрос, который роадмап явно отложил до запуска Фазы 1)

По §2.3: одна таблица `doctor_profiles`, обслуживающая оба модуля. Текущие 11 захардкоженных врачей `medconnect` (Елена Волкова, Михаил Штерн и т.д. — все базируются в Израиле, ориентированы на русскоязычную диаспору, с личными текстами-рекомендациями «endorsement», которые ключевые для модели доверительной сети MedByClick) и 5 захардкоженных врачей `medglobaldb` (международные, с фокусом на академическую статистику: h-индекс, публикации) становятся двумя *представлениями* над одной таблицей, а не двумя схемами. Конкретно:
- Карточки врачей `medconnect` делают запрос `doctor_profiles WHERE vetting_status = 'approved'` и показывают `endorsement`, `credentials`, `casesHandled`, `responseTime`.
- Каталог `medglobaldb` делает запрос к той же таблице шире (включая врачей без рекомендации в стиле `medconnect`) и показывает `institution`, `country`, `hIndex`, `publications`.

Замечание по миграции для Developer'а: существующие 11 врачей `medconnect` и 5 врачей `medglobaldb` — правдоподобные тестовые данные, а не реальные проверенные врачи; не рассматривать их наличие как «это реальные врачи, с которыми можно запускаться». Реальный онбординг врачей требует процесса вёттинга Medical Community (зависимость Фазы 1 по роадмапу), прежде чем `vetting_status` может быть установлен в `approved` для кого-либо.

### 3.2 Реальный флоу записи (заменяет фейковый `setTimeout` в `app/book/BookForm.tsx`)

1. Пациент (авторизованный — запись требует реальной сессии `patient`, это первое место, где авторизация реально что-то блокирует) отправляет существующие поля формы (имя/email предзаполнены из сессии, врач, специальность, ситуация, срочность, язык) через Server Action или Route Handler (выбор за Developer'ом согласно документации Next 16 — оба варианта идиоматичны согласно `node_modules/next/dist/docs/01-app/01-getting-started/15-route-handlers.md` и связанному с ним гайду по Server Actions).
2. Сервер вставляет строку `bookings` со статусом `requested`.
3. Реальная интеграция расписания/календаря со стороны врача в реальном времени не входит в объём этого первого этапа — `scheduled_at` остаётся null, а `status` остаётся `requested`, пока координатор или врач вручную не подтвердит (это соответствует текущей бизнес-модели, описанной в роадмапе/whitepaper: человек-координатор подбирает случаи, а не self-service календарь). Построение живой синхронизации календаря — это реально дополнительный объём работ, который Developer не должен закладывать в эту спецификацию по умолчанию — вернуться к CTO/Product, если окажется, что это ожидается.
4. Личный кабинет пациента (§7) показывает его собственные бронирования по статусу. Кабинет врача (новый) показывает бронирования, назначенные этому врачу.
5. Счётчик `casesHandled` в профиле врача `medconnect` должен вычисляться как `count(bookings where doctor_id = X and status = completed)`, а не оставаться захардкоженным статичным числом — маленькая, но реальная конверсия «из мока в реальность», которую требует определение роадмапа.

## 4. Спецификация истории платежей (`medpayments`)

### 4.1 Чего не хватает на серверной стороне (подтверждено прямой проверкой, §0)

`app/checkout/stripe/StripeForm.tsx` создаёт Stripe `PaymentMethod` на клиенте и дальше ничего с ним не делает. Чтобы сделать это реальным:

1. **Создание `PaymentIntent` на сервере** — новый Route Handler (например, `app/api/payments/stripe/create-intent/route.ts`, по паттерну `app/api/medai/intake/route.ts` с типизированным запросом/ответом и созданием серверного SDK-клиента), который принимает `{ planId, userId }` (из авторизованной сессии, а не от клиента), берёт реальную цену из `plans` в `modules/medpayments/data.ts` (на сервере, чтобы цену нельзя было подделать со стороны клиента), создаёт `PaymentIntent` Stripe на сервере с секретным ключом Stripe (никогда не попадает в браузер — тот же принцип, что уже задокументирован для ключа Anthropic в роуте `medai`), и возвращает `client_secret` фронтенду.
2. **Заменить клиентский флоу** с `createPaymentMethod` + `console.log` на `confirmCardPayment` Stripe (либо перейти на компонент `PaymentElement`, более актуальный паттерн Stripe Elements) с использованием `client_secret` из шага 1.
3. **Эндпоинт webhook** (`app/api/payments/stripe/webhook/route.ts`) для приёма событий `payment_intent.succeeded` (и `.failed`) от Stripe, проверки подписи webhook на сервере и записи/обновления статуса строки `payments` — это авторитетное подтверждение, а не только клиентское состояние «успех» в UI (клиентский успех может обмануть или не сработать; webhook — источник истины «действительно ли мы получили оплату»).
4. **Сохранять строку `payments`** (схема в §2.3), привязанную к `user_id`, в момент создания `PaymentIntent` (статус `pending`), обновляемую webhook'ом до `succeeded`/`failed`. Именно это читает «история платежей в личном кабинете пациента» (§7) — а не лог транзакций в `localStorage`, как текущий мок `MbcDashboard.tsx`.
5. **Замена на боевой ключ только после одобрения QA**, согласно уже существующему замечанию роадмапа по Фазе 0 — текущий захардкоженный `pk_test_TYooMQauvdEDq54NiTphI7jx` — это публичный демо-ключ Stripe, даже не собственный тестовый аккаунт MedByClick; первый шаг Developer'а — завести реальный тестовый аккаунт Stripe для MedByClick и перенести оба ключа в переменные окружения (никогда не хардкодить), независимо от того, когда произойдёт замена на боевые ключи.
6. Согласно роадмапу: **требуется консультация Independent Auditor** перед выходом в прод (плейбук релиза уже отмечает платежи/checkout как требующие консультации) — это уже существующее требование роадмапа, повторено здесь, чтобы не потерялось в деталях.

### 4.2 Что остаётся моком (без изменений относительно роадмапа)

`app/checkout/mbc` и `app/checkout/crypto` остаются симулированными на этом этапе — корректно секвенированы в Фазе 4 вместе с `medtoken`, согласно роадмапу. Не строить реальные крипто/MBC платёжные рельсы в рамках этой спецификации.

## 5. Медицинская история / результаты анализов — новый объём работ, ещё не в роадмапе

### 5.1 Где это должно жить

**Рекомендация: как расширение записи пользователя в `core`, не как новый модуль и не встроено в `medconnect`.** Обоснование: медицинская история принадлежит *пациенту*, независимо от того, какой врач или бронирование её породили — результат анализа от онколога, забронированного через `medconnect`, и результат анализа, загруженный самим пациентом, — это одна и та же категория записи. Моделирование этого как таблицы `medical_history_entries`, ключом которой служит `patient_id` (§2.3), внутри домена данных `core` (даже если UI-поверхность живёт в личном кабинете пациента, а не буквально в `modules/core/`) сохраняет одну идентичность пациента с одной медицинской картой, вместо того чтобы разбрасывать данные о здоровье по границам модулей, где логику контроля доступа пришлось бы дублировать в каждом модуле. `medconnect` и будущие модули (`medtrials`, отслеживание прогресса в `mededu` и т.д.) становятся *потребителями*, которые могут ссылаться на `medical_history_entries` пациента, а не владельцами отдельных копий.

Это действительно новый пункт роадмапа — рекомендуется добавить его в таблицу Фазы 0 `docs/ROADMAP.md` (см. §6, сделано в этом обновлении) как отдельную строку под `core`, а не молча объединять со строкой «реальная база данных, записи пользователей», потому что требование консультации по нему (ниже) существенно отличается от остальной Фазы 0.

### 5.2 Консультация Legal & Compliance — зависимость, а не задача разработки

**Эта роль не квалифицирована в вопросах обработки клинических данных и не та роль, которая должна давать зелёный свет хранению результатов анализов/медицинской истории.** Согласно собственным ограничениям этой роли («если какая-то часть требует участия Legal & Compliance (хранение данных о здоровье) ... отметить это как зависимость»), и согласно уже установленному прецеденту в этом проекте:

- `docs/reports/legal/2026-07-04-medai-llm-data-handling-review.md` — подан в тот же день, что и эта спецификация, — устанавливает, что текст симптомов пациента — это «данные о здоровье — особая категория по режимам, эквивалентным GDPR, и, как только заработает израильское юрлицо, вероятно, также по израильскому Закону о защите частной жизни и Закону о правах пациента», и что DPA, политика хранения данных и (специфически для граждан РФ) решение по обработке с учётом 152-ФЗ — жёсткие требования *до того, как реальные данные пациента начнут передаваться*, а не заполняются задним числом после запуска. Этот вывод был сделан для потоков данных к провайдеру LLM, но лежащие в основе правовые категории (особая категория данных о здоровье по ст. 9 GDPR, израильский Закон о правах пациента после запуска юрлица, 152-ФЗ для граждан РФ) применяются с равной или большей силой к **постоянно хранимым результатам анализов и истории визитов** — возможно, даже сильнее, поскольку это данные, хранящиеся бессрочно, а не единичный вызов API к вендору, покрытому DPA.
- Тот же отчёт отмечает: «собственная политика хранения MedByClick симптомных обращений ... нуждается в зафиксированной политике ... в настоящее время такой политики в этом репозитории не найдено» (§2) — этот пробел *острее* для хранения медицинской истории, чем для транзитного прохождения через LLM, потому что медицинская история спроектирована так, чтобы храниться, а не транзитом проходить.
- Политики конфиденциальности пока не существует (`docs/WHITEPAPER.md`, строка 1002, отмечена как открытый пункт чек-листа в отчёте Legal выше) — построение постоянного хранилища медицинских записей до появления политики конфиденциальности, которая бы им управляла, — это та же ошибка порядка действий, которую Legal & Compliance уже отметила для `medai`.

**Рекомендация Developer'у до этой консультации: строить схему и UI-оболочку только на синтетических/тестовых данных** (тот же паттерн «разблокировано для синтетических данных», уже установленный Legal & Compliance и Medical Advisory для `medai`) — не подключать её к приёму или отображению реальных результатов анализов или записей визитов какого-либо реального пациента, пока Legal & Compliance не рассмотрит:
1. Какая политика хранения применяется к `medical_history_entries`.
2. Нужна ли выбору вендора БД (§2) конкретная конфигурация резидентности данных (например, выбор региона Supabase) с учётом тех же вопросов юрисдикции Израиль/граждане РФ, уже открытых для `medai`.
3. Нужны ли требования шифрования при хранении для файлового/вложенного хранилища документов результатов анализов (`attachment_ref` в §2.3) сверх того, что предоставляет вендор БД по умолчанию.
4. Нужно ли Medical Advisory рассмотреть таксономию `entry_type` по соображениям клинической безопасности (например, должен ли ИИ когда-либо суммировать или отмечать результаты анализов так же, как `medai` делает с симптомным intake — это вне объёма *этой* спецификации, но схема не должна закрывать эту возможность ни в ту, ни в другую сторону без участия Medical Advisory).

**Это отмечено как зависимость, а не решено здесь.** Согласно матрице решений, это, вероятно, пойдёт по тому же маршруту, что и отчёт по обработке данных `medai`: медицинско-регуляторный вывод → Марина (CEO) как основной адресат, копия Medical Advisory, копия Вадиму как владельцу решения по инфраструктуре/вендору — а вопрос «где это хранится» (зависящий от юрисдикции/юрлица) сам может оказаться совместным решением, по той же логике, которую использовал отчёт Legal от 2026-07-04 для потока данных LLM. Задача CTO/Product здесь — секвенировать работу по схеме/UI-оболочке так, чтобы Developer не был полностью заблокирован, а не единолично закрывать правовой вопрос.

Консультация Independent Auditor перед выходом в прод с реальными (не тестовыми) ключами Stripe.
6. **Схема медицинской истории/результатов анализов + UI-оболочка** (§5) — схему и UI можно строить параллельно с пунктами 3–5, как только появится БД (шаг 2), поскольку это зависит от модели пользователя `core`, а не от записи на приём или платежей. **Реальные данные пациента не попадают в неё до тех пор, пока консультация Legal & Compliance из §5.2 не даст добро** — тот же паттерн «сначала синтетические данные», уже установленный для `medai`.
