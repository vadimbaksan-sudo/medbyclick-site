# Спецификация кабинета врача — самообслуживание профиля, регистрация, конвейер бронирований, доступ к медицинской истории

Владелец: **CTO/Product** (`docs/agents/CTO_PRODUCT.md`) · Статус: **Спецификация — готова к передаче Developer'у**
Дата: 2026-07-04
Повод: `docs/reports/product/2026-07-04-core-patient-doctor-cabinets-spec.md` §7 прямо отметил, что «полноценный дашборд врача / поверхность редактирования профиля» требует отдельной последующей спецификации, как только приземлится Фаза 0 (реальная авторизация/БД). Она приземлилась (см. §0 ниже). Это та самая последующая спецификация.

**Согласно ограничениям этой роли (Must-Not-Do): этот документ — спецификация, а не реализация. Developer строит на его основе; кода здесь нет.** Также согласно ограничениям этой роли, она не устанавливает клинические критерии или стандарт допуска врачей — Части 1–4 `docs/reports/medical/2026-07-02-doctor-vetting-standard.md` (Medical Advisory / Medical Community) управляют каждым решением, связанным с проверкой врача, ниже; эта спецификация только описывает, как *продукт* обеспечивает исполнение результатов этого стандарта.

## 0. Отправная точка — что реально существует сегодня (подтверждено прямой проверкой, 2026-07-04)

- `app/doctor-dashboard/page.tsx` — уже построенная минимальная версия. Проверяет `requireRole("doctor")`, загружает `getCurrentDoctorProfile()`, выводит список бронирований через `listBookingsForDoctorProfile()`. Только чтение. Если у авторизованного пользователя нет привязанной строки `doctor_profiles`, показывается статичное сообщение «свяжитесь с координатором». Нет просмотра профиля, нет редактирования профиля, нет изменения статуса бронирования любого рода.
- Таблица `doctorProfiles` в `lib/db/schema.ts` — единственный источник истины, объединяющий `medconnect.Doctor` и `medglobaldb.GlobalDoctor` (согласно спецификации запуска §2.3/§3.1). Значимые колонки: `userId` (nullable — у сид-врачей ещё нет логина), `slug`, `name`, `title`, `specialty`, `subspecialties` (jsonb-массив), `languages` (jsonb-массив), `credentials`, `bio`, `endorsement`, `avatarUrl`, `casesHandledOverride`, `responseTime`, `institution`, `country`, `city`, `hIndex`, `publications`, `verified` (boolean), `vettingStatus` (enum: `pending` / `approved` / `rejected`).
- `lib/db/queries/doctors.ts` — сегодня это слой запросов только на чтение (`getDoctorProfileById`, `getDoctorProfileBySlug`, `listMedconnectDoctors` с фильтром `vettingStatus === "approved"`, `listGlobalDbDoctors`, `getCasesHandledCount`, вычисляемый из завершённых бронирований). Функции обновления/вставки для `doctor_profiles` пока не существует вообще — эта спецификация описывает, каким должен быть контракт этой функции обновления.
- `lib/db/queries/bookings.ts` — `createBooking`, `listBookingsForPatient`, `listBookingsForDoctorProfile`, `findDoctorProfileBySlugOrId`. Функции изменения статуса пока не существует (нет `updateBookingStatus`, нет поля заметок в `bookings` вообще).
- `lib/auth/dal.ts` — устоявшийся паттерн авторизации: `verifySession()` (проверяется сервером через Supabase `getUser()`, никогда не через клиентски заявленную роль), `getCurrentUser()`, `getCurrentDoctorProfile()`, `requireRole(role)` (с редиректом, для серверных компонентов), `getAuthorizedUser(allowedRoles?)` (возвращает результат, для Server Actions/Route Handler'ов — возвращает `{error: "unauthenticated"|"forbidden"}` вместо редиректа). Каждое правило контроля доступа в этой спецификации должно идти через этот DAL, а не через новую отдельную проверку — это устоявшаяся конвенция, и Developer должен её расширять, а не обходить.
- `lib/auth/actions.ts` `registerPatient()` — единственный работающий Server Action регистрации сегодня. Его собственный комментарий гласит: «Самостоятельная регистрация врача явно вне объёма этого этапа... каждый аккаунт, созданный через эту форму, имеет role: 'patient'». Это подтверждает, что сегодня **нет вообще никакого пути регистрации врача** — ни самостоятельного, ни через администратора. Это реальный пробел, который закрывает эта спецификация.
- `docs/reports/medical/2026-07-02-doctor-vetting-standard.md` — стандарт проверки врачей от Medical Advisory. Часть 1 перечисляет семь обязательных барьеров допуска (проверка лицензии, таксономия специальности, дисциплинарная история, институциональная принадлежность, языковая компетенция, согласие с правилами поведения, согласие на отслеживание исходов). Часть 2 закрепляет первичную проверку и проверку рекомендаций за Medical Community, при этом **финальное клиническое решение о допуске закреплено за Medical Advisory и не подлежит делегированию**. Эта спецификация трактует поле `vettingStatus` как поле, кодирующее «прошёл ли врач Части 1–2», и его конечный автомат управляется этим процессом, никогда — самим врачом.

## 1. Самообслуживание профиля врача

### 1.1 Поля, редактируемые врачом

Врач с привязанной строкой `doctor_profiles` (`userId` установлен) может редактировать, только в своей собственной строке:

| Поле | Обоснование |
|---|---|
| `bio` | Свободный текст самоописания; риска клинического заявления не больше, чем уже закрыто проверкой credentials |
| `credentials` | Текстовое описание степеней/подготовки — см. оговорку §1.3 ниже, это *отображаемый* текст, а не заявление о проверенном статусе |
| `languages` (jsonb-массив) | Врач — авторитетный источник того, на каких языках он лично говорит |
| `subspecialties` (jsonb-массив) | Уточнение внутри специальности; не меняет категорию таксономии, от которой зависит маршрутизация |
| `responseTime` | Самозаявленное обязательство, согласуется с барьером 6 Части 1 стандарта проверки (согласие с правилами поведения/времени ответа) |
| `avatarUrl` | Только оформление |
| `title` | Только оформление (например, «MD», «Проф.») |
| Настройки контактов/уведомлений, если появятся позже (нет в текущей схеме) | Управление аккаунтом, не клиническое |

### 1.2 Явно НЕ редактируемое врачом (обеспечивается сервером, не просто скрыто в UI)

| Поле | Кто может изменить | Почему |
|---|---|---|
| `vettingStatus` | Medical Community (рабочий процесс) → записывается действием администратора/ревьюера, никогда собственным Server Action врача | Часть 2 стандарта проверки, шаг 5: «финальное клиническое решение о допуске... не подлежит делегированию». Врач, редактирующий свою строку, никогда не должен иметь возможность установить это поле, даже косвенно (например, через общий action «обновить профиль», случайно включивший это поле в белый список). |
| `verified` | Так же, как выше | То же обоснование — это булев флаг, переключающий профиль из «не доступен для бронирования» в «доступен» в фильтре `listMedconnectDoctors()`; самостоятельное объявление этого флага разрушает весь рабочий процесс проверки. |
| `specialty` | Только администратор / Medical Community, по крайней мере при первичной проверке | Изменение основной специальности после допуска фактически означает повторный вход в барьер таксономии специальности (Часть 1, барьер 2) — должно требовать повторного ревью, а не самостоятельного редактирования. Рекомендация: врач может *запросить* смену специальности через форму, направляемую в Medical Community, а не через прямое редактирование поля. |
| `institution`, `country`, `city`, `hIndex`, `publications` | Только администратор / Medical Community | Это ровно те поля, которые барьер 4 Части 1 (проверка институциональной принадлежности/рекомендаций) сверяет с первичным источником. Самостоятельное редактирование позволило бы врачу заявить принадлежность или число публикаций, которые никто не проверял. |
| `casesHandledOverride` | Только администратор (в идеале — устарело, см. §3.4) | Сегодня это поле существует только как запасной вариант для сид-данных врачей без реальной истории бронирований; у реального врача число случаев должно вычисляться через `getCasesHandledCount()` (реальные завершённые бронирования), а не быть самостоятельно редактируемым числом. Возможность врача завысить своё число случаев — проблема целостности данных. |
| `slug` | Только администратор | Стабильный идентификатор URL; изменение ломает существующие ссылки (комментарий в схеме уже отмечает, что это перенесено из мок-id для стабильности ссылок). |
| `endorsement` | Только Medical Community | Это явно *чужая* рекомендация о враче (например, институциональная рекомендация), а не самостоятельно написанный контент — врач, пишущий собственную «рекомендацию», разрушает её смысл. |

### 1.3 Паттерн серверного обеспечения (конкретно, согласуясь с существующей конвенцией DAL)

Рекомендуется новый Server Action `lib/doctor-profile/actions.ts`, например `updateOwnDoctorProfile(formData)`, который:

1. Вызывает `getAuthorizedUser(["doctor"])` из `lib/auth/dal.ts` (существующий паттерн с возвратом результата, используемый для Server Actions) — никогда не доверяет id профиля/врача, переданному клиентом.
2. Загружает собственную строку `doctor_profiles` вызывающего через `getCurrentDoctorProfile()` и выводит id строки *из неё*, никогда из входных данных формы — именно это не даёт врачу передать чужой `id` и отредактировать чужую строку.
3. Валидирует вход по Zod-схеме (по паттерну `RegisterFormSchema`/`LoginFormSchema`, уже существующему в `lib/auth/validation.ts`), форма которой **содержит только белый список §1.1** — `vettingStatus`, `verified`, `specialty`, `institution`, `country`, `city`, `hIndex`, `publications`, `casesHandledOverride`, `slug`, `endorsement` не должны появляться как разбираемые ключи в этой схеме вообще, а не просто отбрасываться после парсинга. Поле, отсутствующее в схеме, невозможно протащить через сконструированный запрос; поле, которое присутствует, но тихо отбрасывается, — это уязвимость, до которой один рефакторинг.
4. Выполняет Drizzle `update`, ограниченный `eq(doctorProfiles.userId, session.userId)`, а не id, прочитанным из запроса — вторая подстраховка сверх белого списка.

Это та же форма, что и существующий паттерн `registerPatient()` («валидировать → авторизовать → ограниченная запись») — не новая архитектурная идея, просто тот же паттерн, применённый к обновлению вместо вставки.

## 2. Регистрация врача

### Рекомендация: самостоятельная регистрация с `vettingStatus: "pending"` по умолчанию, с последующим ревью Medical Community — а не только через администратора.

Обоснование, привязанное к существующему документу о рабочем процессе проверки и существующему паттерну регистрации пациента:

- Процесс Части 1–2 стандарта проверки уже спроектирован вокруг *ревью заявки*, а не *создания аккаунта для кого-то*. «Приём заявки (Medical Community)» указан как шаг 1 Части 2 — стандарт предполагает, что заявка уже существует. Самостоятельная регистрация — это то, что и производит эту заявку; регистрация только через администратора означала бы, что Medical Community должна вручную создавать каждый аккаунт врача до начала проверки, что дублирует работу, которую уже выполняет сам процесс проверки.
- Это повторяет уже построенный паттерн `registerPatient()`: Supabase Auth `signUp()` создаёт идентичность, затем в том же action через Drizzle создаётся соответствующая строка `public.users`. Самостоятельная регистрация врача должна следовать той же форме — `role: "doctor"` вместо `"patient"` — чтобы Developer расширял проверенный паттерн, а не изобретал второй.
- `vettingStatus` уже по умолчанию `"pending"` в схеме (`vettingStatusEnum(...).default("pending")`) — это уже безопасное значение по умолчанию; самостоятельная регистрация не требует изменения схемы, только нового Server Action и вставки строки `doctor_profiles` вместе со строкой `users`.
- Не подлежит обсуждению, согласно формулировке задачи и стандарту проверки: **самостоятельно зарегистрированный врач никогда не должен быть доступен для бронирования до тех пор, пока Medical Community/Medical Advisory его не допустят.** `listMedconnectDoctors()` уже фильтрует по `vettingStatus === "approved"` — пока action регистрации не устанавливает также `verified: true`, врач в статусе pending автоматически исключается из списка доступных для бронирования без какой-либо дополнительной логики. Это уже сильная существующая страховочная сетка; action регистрации не должен её переопределять.

### Конкретный флоу

1. Врач заходит на новый маршрут `/register/doctor` (параллельно `/register`, не слияние с формой пациента — другие обязательные поля: специальность, заявленные credentials, данные о лицензии для проверки Medical Community).
2. Server Action создаёт идентичность Supabase Auth + строку `users` (`role: "doctor"`) + строку `doctor_profiles` с установленным `userId`, `vettingStatus: "pending"` (по умолчанию, не переопределять), `verified: false` (по умолчанию, не переопределять) и теми самозаявленными полями, которые собирает форма (имя, специальность, заявленные credentials, языки) — это ровно те поля из §1.1, редактируемые врачом; ничего из §1.2 не устанавливается и при регистрации тоже.
3. Зарегистрированный, но ожидающий проверки врач может войти и попасть на `/doctor-dashboard`, но увидит состояние «ожидает проверки» (расширение существующего состояния «профиля врача пока нет» в `app/doctor-dashboard/page.tsx` до отдельного состояния «профиль существует, проверка ожидается») вместо списка бронирований, поскольку у ожидающего/не допущенного врача бронирований назначено быть не должно в принципе.
4. Medical Community проводит Части 1–2 стандарта проверки вне платформы (первичная проверка лицензии, рекомендации, присвоение таксономии специальности) точно так же, как сегодня — эта спецификация не меняет этот процесс, только даёт ему реальную заявку вместо её отсутствия.
5. При одобрении действие администратора/роли Medical Community (вне рамок этого дашборда, вероятно — облегчённая внутренняя административная поверхность, здесь не детализируется) переключает `vettingStatus: "approved"` и `verified: true`. Это единственное место, где эти два поля меняются, и оно должно проходить через ту же проверку в духе `getAuthorizedUser`, ограниченную ролью администратора/ревьюера, никогда — собственным действием врача.

### Что это НЕ решает

- Внутренняя административная/ревьюерская поверхность, которую Medical Community реально использует для переключения `vettingStatus`, здесь не специфицируется — отмечаю это как небольшую сопутствующую последующую задачу (вероятно, маршрут с ролью `admin` или даже прямое действие в БД, выполняемое доверенным оператором в ближайшей перспективе, учитывая текущий размер команды). Это не блокирует принятие этой спецификации; флоу регистрации работает в любом случае, пока поле рано или поздно переключается через авторизованный путь.

## 3. Конвейер бронирований для врачей

Напоминание об объёме согласно роадмапу: **на этом этапе нет живого календаря или самостоятельного планирования** — человек-координатор остаётся в цикле для реального планирования. Этот раздел о том, что врач делает с бронированием, которое координатор уже направил ему, а не о системе планирования.

### 3.1 Текущее состояние

`app/doctor-dashboard/page.tsx` выводит список бронирований, назначенных профилю врача, только для чтения, показывая `specialty`, `requestedAt`, `situationNotes`, `status`. Изменений не существует.

### 3.2 Что врач должен уметь делать с назначенным бронированием

| Действие | Переход статуса | Заметки |
|---|---|---|
| **Подтвердить** | `requested` → `confirmed` | Врач подтверждает, что возьмёт этот случай. Простое, низкорисковое действие — рекомендую строить первым. |
| **Отметить завершённым** | `confirmed` → `completed` | Врач сигнализирует, что консультация состоялась. Это также то, что питает `getCasesHandledCount()`, поэтому этот переход имеет наибольший побочный эффект (целостность счётчика случаев, см. примечание §1.2 о `casesHandledOverride`) — рекомендую требовать `confirmed` как единственно допустимое предыдущее состояние (без прыжка напрямую из `requested` в `completed`), чтобы в аудиторском следе всегда был шаг подтверждения. |
| **Добавить заметки** | Без смены статуса | Свободное текстовое поле, авторства врача, например `doctorNotes` (новая колонка — в таблице `bookings` сейчас нет поля заметок вообще, только `situationNotes` авторства пациента). Рекомендую отдельное поле, а не перезапись `situationNotes`, чтобы текст приёма от пациента и клинические заметки врача никогда не смешивались в одной колонке. |
| **Отклонить** | `requested`/`confirmed` → обратно в `requested` с отвязкой врача (`doctorId: null`), **не** `cancelled` | Отклонение — это «направьте это кому-то ещё», а не «этого бронирования не было». Рекомендую, чтобы это всегда уведомляло/помечало координатора, а не автоматически переназначало другому врачу — логика переназначения (правило подбора, доступность) — территория координатора/рабочего процесса подбора, явно не задача этого дашборда. |

### 3.3 Что врач НЕ должен уметь делать

- Переназначить бронирование конкретному другому врачу напрямую (это решение подбора/координации, вне рамок здесь — отклонение с возвратом в пул — единственный рычаг врача).
- Менять `patientId`, `urgency`, `scheduledAt` или `source` — это либо принадлежит пациенту/координатору, либо это метаданные рабочего процесса, не для редактирования врачом.
- Отменять бронирование полностью (`status: "cancelled"`) — рекомендую оставить это только за координатором/администратором, поскольку отмена, вероятно, имеет последствия для платежей/возвратов (связь с таблицей `payments`), выходящие за пределы полномочий врача запускать в одностороннем порядке.

### 3.4 Паттерн обеспечения

Та же форма DAL, что и в §1.3: Server Action в духе `updateBookingAssignedToSelf(bookingId, action)`, который вызывает `getAuthorizedUser(["doctor"])`, затем ограничивает Drizzle `update` условием `and(eq(bookings.id, bookingId), eq(bookings.doctorId, doctorProfile.id))` — врач может изменять только то бронирование, которое уже назначено его собственному `doctor_profiles.id`, никогда произвольный id бронирования. Требует добавления функции обновления в `lib/db/queries/bookings.ts` (сейчас её нет) плюс миграции, добавляющей `doctorNotes` в таблицу `bookings`.

## 4. Взаимодействие с медицинской историей — зависит от параллельного ревью Legal & Compliance

**Этот раздел предлагает правило доступа; он его не утверждает.** Согласно ограничениям этой роли, разрешение юридического вопроса о медицинских данных явно не задача этой спецификации — это `docs/reports/legal/2026-07-04-medical-history-data-handling-review.md`, выполняется параллельно. Всё ниже — проектное предложение, зависящее от одобрения этого ревью, следующее тому же паттерну «сначала синтетические данные», уже установленному для `medical_history_entries` (колонка `isSynthetic` в `lib/db/schema.ts`, жёстко по умолчанию `true`, с комментарием в слое запросов, отмечающим: «Функции вставки для этой таблицы нигде в кодовой базе сейчас не существует — намеренно»).

### 4.1 Предлагаемое правило доступа (только проект, не принято до одобрения Legal)

Врач может читать (а позже — писать) строки `medical_history_entries` для конкретного пациента **только если существует бронирование, связывающее этого врача и этого пациента со статусом `confirmed` или `completed`** — никогда безусловное «врач может видеть историю любого пациента», и никогда доступ по одному лишь статусу `requested` (просто запрошенное, ещё не подтверждённое бронирование не должно открывать доступ к истории).

Отмечаю явно, как и было поручено: это должна быть **проверка на уровне БД, а не только на уровне приложения** — то есть не просто «Server Action проверяет наличие бронирования перед запросом», а проверка, структурно сложная для обхода (например, политика row-level security Postgres на `medical_history_entries`, соединяющаяся через `bookings`, или как минимум запрос, всегда идущий через соединение с `bookings`, а не когда-либо принимающий голый `patientId` от авторизованного как врач вызывающего). Текущая функция `getSyntheticMedicalHistoryForPatient()` принимает голый `patientId` без какого-либо соединения с врачом/бронированием — эта форма нормальна для текущего случая использования «пациент смотрит свою собственную синтетику», но явно неверная форма для расширения на доступ врача без добавления соединения через связь бронирования, описанного выше.

### 4.2 Что конкретно зависит от параллельного ревью Legal

- Получат ли врачи вообще какой-либо реальный (не синтетический) доступ на чтение/запись к медицинской истории в обозримом будущем, или это останется поверхностью только для пациента и только синтетической, пока Legal не прояснит вопросы хранения/резидентности/юрисдикции.
- Последствия резидентности данных того, что врач (который может находиться в другой юрисдикции, чем пациент) читает данные о здоровье пациента — это ровно предмет ревью Legal, здесь не решается.
- Любой путь записи для врачей вообще — сейчас функции вставки для этой таблицы не существует ни от одного вызывающего, ни пациента, ни врача. Добавление пути записи для врача — строго более крупное изменение, чем путь чтения, и должно ждать одобрения Legal ещё дольше, чем путь чтения.

### 4.3 Что НЕ зависит от ревью и можно утверждать уже сейчас

Флаг `isSynthetic` и состояние «функции вставки не существует» остаются ровно такими, какие они есть, пока Legal их не одобрит — эта спецификация не предлагает ослабление этого барьера. Если поверхность медицинской истории для врача будет построена до завершения ревью Legal, она должна отображать только синтетические сид-данные, идентично тому, как это сейчас делает дашборд пациента, с той же явной маркировкой «пример данных», уже установленной в кодовой базе (согласно паттерну честной маркировки дашборда пациента, отмеченному в §7 спецификации запуска).

## 5. Явно вне объёма (отложено, а не забыто)

| Пункт | Почему отложено |
|---|---|
| **Обмен сообщениями в реальном времени между врачом и пациентом** | Инфраструктуры чата не существует; также поднимает те же вопросы обработки данных, смежные с медицинской историей, что и §4 (содержимое сообщений может содержать клиническую информацию), не имея пока одобрения Legal, на которое можно было бы опереться. |
| **Дашборды аналитики/заработка для врача** | Не существует модели выплат врачам в `medpayments`/`medtoken` — это вопрос Фазы 4 (токен-гейтед) или как минимум отдельного расширения `medpayments`, а не этого дашборда. Построение поверхности заработка без реального содержания повторяет ошибку, которую роадмап уже отмечает для UI кошелька `medtoken` («производит UI, к которому нечего подключить»). |
| **Мультиклиничные аккаунты персонала** | Текущая схема — одна строка `doctor_profiles` на отдельного врача с связью 1:1 `userId` — нет концепции сущности клиники, ролей персонала под клиникой или общих клиничных входящих бронирований. Это расширение модели данных, а не функция дашборда, и ничем в текущих фазах роадмапа не запускается. |
| **Живой календарь / самостоятельное планирование** | Уже явно вне объёма согласно роадмапу — повторяю здесь, чтобы ничто в дополнениях к конвейеру бронирований §3 не читалось как система планирования. Человек-координатор остаётся в цикле для фактической установки времени `scheduledAt` бронирования. |
| **Изменение специальности/таксономии по инициативе врача без ревью** | Согласно §1.2, изменение специальности трактуется как повторный вход в барьер проверки, а не самостоятельное редактирование — путь через запрос (врач запрашивает, Medical Community рассматривает) назван как рекомендация, не специфицирован подробно здесь, поскольку это небольшой вариант того же флоу регистрации/проверки из §2. |

## 6. Сводка требуемых консультаций (для осведомлённости Developer'а — эта роль их не утверждает)

- **Medical Advisory / Medical Community**: любое изменение полей или процесса, смежных со стандартом проверки (§1.2, §2), должно оставаться согласованным с `docs/reports/medical/2026-07-02-doctor-vetting-standard.md`; эта спецификация не меняет этот стандарт, только выстраивает продукт вокруг него.
- **Legal & Compliance**: правило доступа к медицинской истории в §4 — это предложение, а не одобрение; реальный (не синтетический) доступ врача к `medical_history_entries` ждёт `docs/reports/legal/2026-07-04-medical-history-data-handling-review.md`.
- **QA/GStack**: согласно правилам передачи, консультация перед пометкой любого получившегося релиз-кандидата как готового, особенно для серверного обеспечения в §1.3/§3.4 — это ровно тот код границы авторизации, который QA должен проверить на невозможность обхода сконструированным запросом.
